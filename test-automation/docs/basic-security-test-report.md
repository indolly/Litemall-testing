# Litemall 基础安全测试报告

## 1. 测试结论

- 执行日期：2026-10-18
- 测试环境：Windows 本地环境、Litemall WX API、MySQL 5.7
- 测试方式：Python + Requests + Pytest + PyMySQL
- 安全子集：20 项
- 执行结果：18 passed，2 xfailed
- 全量接口回归：44 项，41 passed，3 xfailed

`xfail` 表示用例按安全预期执行后复现了已知缺陷，不表示产品功能通过。

执行命令：

```powershell
python -m pytest -m security -q
```

## 2. 测试思路

本轮不做复杂渗透测试，重点验证接口的四层控制：

1. 认证：没有 Token、伪造 Token、过期 Token 是否被拒绝。
2. 对象级授权：即使已经登录，也不能操作其他用户的地址、订单和购物车。
3. 输入与业务状态：篡改用户 ID、地址 ID、购物车 ID、缺少字段或重复提交时，系统不能产生越权或重复数据。
4. 信息暴露：正常和异常响应不能返回密码、会话密钥、内部账号字段、堆栈和 SQL 信息。

判断安全结果时不能只看 HTTP 200。Litemall 使用 HTTP 200 承载业务结果，因此还要校验 `errno`、`errmsg`、数据库归属、订单状态和逻辑删除状态。

## 4. 已确认问题

### SEC-01 跨用户提交购物车（高风险）

用户 B 携带自己的有效 Token，但把请求体中的 `cartId` 修改为用户 A 的购物车 ID，接口仍能创建归属于用户 B 的订单，并逻辑删除用户 A 的购物车记录。

根因是订单提交按 `cartId` 调用了只按主键查询的方法，没有同时校验 `user_id` 和 `deleted=false`。

建议修复：

- 将 `cartService.findById(cartId)` 改为 `cartService.findById(userId, cartId)`；
- 查询不到记录时返回统一的参数值错误或无权限错误；
- 在同一事务中再次校验购物车归属、未删除状态和商品库存；
- 增加跨用户回归用例，确保修复不会被后续改动破坏。

### SEC-02 相同购物车重复提交（高风险）

同一 `cartId` 首次提交后购物车已逻辑删除，但第二次提交仍能再次创建订单并重复扣减库存。

根因与 SEC-01 相同：订单提交查询没有过滤 `deleted=true`，同时接口缺少幂等控制。

建议修复：

- 首先使用包含 `userId` 和 `deleted=false` 的购物车查询；
- 为下单请求增加幂等键，并在服务端保存处理结果；
- 使用数据库唯一约束或原子状态更新兜底；
- 并发场景下结合事务、乐观锁和库存条件更新验证“只成功一次”。

## 5. 其他代码审查风险

- JWT 密钥直接写在 `JwtHelper` 源码中，应改为环境变量或密钥管理服务，并支持轮换。
- `logout` 当前只返回成功，没有服务端失效列表；Token 在到期前仍可能继续使用。生产系统应根据风险选择短有效期 + 刷新令牌，或增加撤销机制。
- 生产环境建议使用 HTTPS，日志中对 Token、手机号、收货地址进行脱敏。
- 登录、验证码和下单接口应增加速率限制、失败次数限制与审计记录。
